## Реализация

Четвёртый инструмент batch_update_instances, POST instances/batch и отдельный scope. 1…100 уникальных существующих комнат, строгие changes как у single update, одна expectedRevision. Синтаксис всех записей проверяется до чтения owner-проекта; все IDs/revision проверяются до применения. Копия проходит итоговую проверку материалов/ядра/бюджета/пересечений, затем один прежний CAS UPDATE. Успех даёт revision+1, включая те же значения; обмен позициями разрешён. Старые scopes не расширяются; отдельный batch scope не даёт get/validate/single. UI включает по умолчанию только get+validate. Формат 1, SDK 1.32.2, package lockfiles, хранилище, writer Java 1.21.5/DataVersion 4325, sessionStorage/dirty и 3D не менялись.

Проверены initialize/tools/list/tools/call нового и прежних трёх инструментов; strict input/output schemas, границы 0/1/100/101, уникальность ID, unknown keys/IDs, типы, размеры, materials/properties, запрещённая смена definitionId, итоговое пересечение и общий бюджет, HTTP и UTF-8 MCP payload >2000000 байт. Schema и runtime согласованы для синтаксиса; межэлементная уникальность ID, общий byte limit и геометрические ограничения — runtime, как описано в контракте. Raw stdout содержит JSON-RPC, секрет fixture не отражается в stderr/ошибках. На клиенте нет retry/redirect. Loopback fixture действительно меняет свой сохранённый снимок перед разрывом ответа: NETWORK_ERROR, затем повтор со старой revision → 409 без второго применения. Это HTTP fixture, не Neon/OAuth E2E.

SQL fixture проверяет persisted Map, а не только возвращённый ответ: ровно один UPDATE/revision+1, отсутствие частичных изменений при ошибке последнего элемента, допустимый swap, no-op revision, неизменность входных аргументов и IDs. Гонки batch↔batch, batch↔single и batch↔реальный handler PUT дают одного победителя и 409. Проверены owner/project isolation, legacy scopes без расширения, batch-only запрет get/single/validate, выбор всех четырёх scopes, expiry/revoke, session-only выдача, Origin, 401/403/404/409/413/415 и безопасные ошибки. HTTP-коды 400/401/403/404/409/413/415/503 маппятся через настоящий SDK. Здесь identity подменена только в отдельном тестовом процессе, Google OAuth не имитируется как живая приёмка.

Отдельный Neon-тест использует реальный getSql с подсчётом запросов и уникальных служебных owners/UUID: один owner-read и один UPDATE при swap, сохранённые строки читаются повторно через сервис и напрямую SQL; ошибка последнего элемента, unknown instance, overlap и общий бюджет оставляют документ/updatedAt/revision прежними. Проверены owner isolation, stale replay, no-op revision+1 и конкурентные batch↔batch/single/сервис полного PUT. Ровно один победитель, document.revision совпадает с колонкой. Все четыре созданных тестовых проекта удалены штатным сервисом; пустой список тестового owner подтверждён. Пользовательские проекты/делегирования не использованы. Тест доступен через `npm run test:structure-batch-neon`; реальный запуск выполнен напрямую после сборки сервисов. При отсутствии DATABASE_URL тест явно skipped; в этом запуске skip=0.

По react-best-practices проверены узкие изменения TSX: состояние выбора и disabled fieldset прежние, новый checkbox имеет label, запись запускается только событием; новых effects/клиентских SDK/DB импортов нет. В `.next/static` JavaScript не найдены @modelcontextprotocol, SDK и StdioServerTransport (CSS-класс structure-mcp-help ожидаем и не означает SDK).
