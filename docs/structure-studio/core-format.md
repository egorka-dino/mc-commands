# Structure Core: формат 1

Публичный интерфейс: `app/structure-core/index.ts`; типы: `types.ts`. Зависимостей от рендера, серверной среды и MCP нет.

```ts
import { createStoneRoomProject, generateProject, serializeProject, deserializeProject } from "../../structure-core";

const project = createStoneRoomProject("my-project", "room-1");
project.instances[0].parameters.height = 10;
project.instances[0].parameters.doors.east = true;
project.instances[0].parameters.wall.id = "minecraft:deepslate_bricks";
const { cells, conflicts } = generateProject(project);
const restored = deserializeProject(serializeProject(project));
```

Пример пути импорта приведён для компонента в `app/components/structures/`. IDs передаёт вызывающий код; при генерации и загрузке ядро не меняет их. `createStoneRoomProject` создаёт одну комнату. Пустые definitions/instances также допустимы через `parseProject`.

Проект содержит ровно `formatVersion: 1`, `id`, `name`, `revision`, `definitions`, `instances`. Определение: `id`, `generator`, `parameters` (значения по умолчанию). Экземпляр: `id`, `definitionId`, полный снимок `parameters`, `position: {x,y,z}`, `rotation`. Параметры экземпляра авторитетны: изменение defaults определения не меняет существующие экземпляры. Геометрия в JSON не дублируется. `revision` задаётся серверным хранилищем: 1 при создании, затем +1 при атомарном сохранении с expectedRevision. Ядро само не увеличивает его; локальное редактирование сохраняет последнюю известную версию.

Stone Room использует `width`, `length`, `height`, `wallThickness: 1`, `wall`, `floor`, `ceiling`, `doors: {north,east,south,west}`. Начальные значения: 11×11×8, stone_bricks, все двери выключены. Ширина/длина нечётные 5…129, высота 6…128. Двери всегда 3×4, начиная с Y=1, центрированы по нечётному размеру стены. Пол Y=0 и потолок Y=height−1 всегда целы. Порт создаётся только для включённой двери; его position — центр нижнего ряда проёма, width=3, height=4. ID порта сохраняет локальное имя при повороте, direction становится мировым направлением.

Каждая ячейка содержит `position` и `kind`: `solid` дополнительно содержит `state: {id, properties}`, `air` означает очистить блок, `void` — не трогать мир. Stone Room выдаёт полную ограниченную область с solid/air; void предусмотрен типом, но этот генератор его не выдаёт. За пределами выданного объёма нет операции. Проверяется синтаксис namespaced ID/свойств, но не существование блока или комбинации свойств в реестре конкретной версии Minecraft. Воздух и structure_void запрещены как solid.

`generateStoneRoom` выдаёт локальную геометрию. `generateInstance` поворачивает её вокруг (0,0,0), затем переносит. X восток, Z юг; 90° переводит north в east, `(x,y,z) → (-z,y,x)`. У повёрнутой комнаты возможны отрицательные локальные координаты; экспорт должен вычислять реальные min/max, а не обрезать их. Поддерживаются 0/90/180/270, facing, axis, числовой rotation 0…15 и cardinal-свойства соединений. Поворот свойств shape/orientation пока явно отклоняется: сложные рельсы/лестницы требуют отдельного адаптера. Поддержка других directional-свойств и полноценная проверка Minecraft registry не заявляются.

`generateProject` проверяет модель, объединяет ячейки и возвращает конфликты с координатой и IDs обоих владельцев. Любое пересечение двух объёмов, включая air/air и одинаковый solid, считается конфликтом. Это консервативная политика первой версии: автоматического вырезания общей стены ещё нет. При конфликте в cells остаётся первая ячейка; потребители обязаны обработать conflicts до сохранения результата сборки/экспорта. `void` пропускается. Конфликтная модель может сериализоваться для последующего исправления пользователем.

Строгий разбор отклоняет неизвестные/отсутствующие поля, неизвестную версию/генератор, неверные размеры, повторяющиеся IDs и потерянные ссылки. Вложенные модули пока не поддерживаются; циклические ссылки форматом не допускаются. Лимиты прототипа: 100 definitions, 100 instances, суммарно 250000 генерируемых ячеек, JSON до 2000000 символов при загрузке, координаты входа ±30000000. Это защитные пределы прототипа, не ограничения конечного Minecraft-конструктора; для больших построек понадобятся ленивые секции и отдельный бюджет.

`serializeProject`/`deserializeProject` сохраняют параметры, связи definitionId и revision. Это JSON-кодек; облачное хранилище поверх него реализовано в app/server/structure-projects.ts и дополнительно отклоняет конфликты геометрии. Все функции генерации и разбора не изменяют входную модель. Незнакомые версии не мигрируются молча.

Проверки: `npm run test:structure-core`, `npx tsc --noEmit`, `npm run build`. Тесты покрывают точный объём и оболочку, 16 комбинаций дверей, размеры и материалы, повороты прямоугольной комнаты и портов, BlockState, JSON round trip, ограничения, конфликт solid/air и совокупный бюджет.


## Адаптер Sponge v3 (этап 5)

Формат 1 и генератор не меняются. Серверный `exportStructureSchematic(unknown)` валидирует проект, ограничивает материалы семью состояниями редактора для Java 1.21.5/DataVersion 4325, отклоняет конфликты и передаёт сгенерированные ячейки в `encodeSchematic`. Последний — внутренний адаптер, не HTTP-контракт для клиентских ячеек. Gzip NBT: пустой root → Schematic, Version=3, Blocks.Palette и VarInt Blocks.Data. Размеры max−min+1, Offset=min, WorldEdit Origin=[0,0,0]; индексы (x−minX)+(z−minZ)*Width+(y−minY)*Width*Length. Explicit air очищает мир, void и отсутствующие ячейки bounding box кодируются structure_void; нужен обычный WorldEdit `//paste` без -a/-v. Помимо бюджета ядра ограничен плотный bounding box (250000 ячеек/65535 по оси). Пустой проект сохранять можно, экспортировать нельзя. Entities, block entity NBT и биомы не экспортируются; существование произвольных core BlockState вне семи материалов этим этапом не обещается.


## Batch существующих экземпляров

Формат 1 не расширяется. [batch_update_instances](batch-contract.md) меняет параметры/позицию/поворот 1…100 существующих комнат одного проекта. Все changes разбираются прежним ядром, итоговый общий бюджет и пересечения проверяются целиком. Обмен позициями допустим; IDs и definitionId неизменны. Один успешный CAS повышает revision на 1, включая no-op значения. Writer и целевая версия экспорта остаются прежними.
