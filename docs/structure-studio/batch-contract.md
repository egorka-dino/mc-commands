# Атомарное изменение комнат: контракт до реализации

1 ноября 2026. Дополнение к mcp-contract.md; формат проекта 1, SDK 1.32.2 и протокол stdio не меняются.

`batch_update_instances({projectId, expectedRevision, updates:[{instanceId, changes}]}) → {document: StructureProject, updatedAt: string}`. POST `/api/structures/:id/instances/batch` принимает ровно `{expectedRevision, updates}`. MCP делает один HTTP-запрос. projectId — UUID прежнего формата, expectedRevision — целое 1…2147483646. updates — массив 1…100 элементов с уникальными instanceId (непустая строка 1…200 символов). Все объекты strict: неизвестные/отсутствующие поля, неверные типы, пустой массив, дубли и пустые changes отклоняются.

changes совпадает с update_instance: непустое подмножество parameters (полный StoneRoomParameters), position (целые x/y/z ±30000000), rotation (0/90/180/270). Нельзя менять IDs, definitionId, имя проекта, создавать/удалять комнаты или передавать JS/NBT/SQL. Размеры, ссылки, 100 definitions/instances и суммарный бюджет 250000 ячеек — общее ядро. Семь прежних материалов, properties строго пустой объект. JSON Schema tools/list и runtime parser используют общие схемы; размер сериализованного UTF-8 запроса ограничен 2000000 байтами (в HTTP также независимо от Content-Length). Межэлементная уникальность instanceId и общий byte limit проверяются runtime, поскольку стандартная JSON Schema не выражает их для такого объекта.

Сервис сначала разбирает синтаксис всех изменений, один раз читает owner-проект, проверяет expectedRevision и наличие всех IDs. Создаёт независимую копию, применяет все изменения, валидирует итоговый снимок целиком и вызывает один существующий CAS UPDATE по id/user_id/revision. Проверок промежуточных пересечений нет: обмен позициями разрешён, если финальный снимок допустим. Нет цикла single update, промежуточных записей или компенсаций. Успех сохраняет полный документ с revision+1 ровно один раз, включая те же значения. IDs и входные объекты сохраняются.

Отдельный scope `batch_update_instances` выбирается явно. Старые grants не расширяются, update_instance не даёт batch, batch не даёт single/get/validate. Старые три scopes продолжают работать без миграции. По умолчанию UI включает только get+validate; оба вида записи выключены. Session owner может использовать route с прежним same-origin контролем; Bearer проверяет проект, scope, expiry/revocation. Выпуск/список/отзыв остаются только session owner.

Ошибки: 400 INVALID_ARGUMENT (синтаксис, дубли, поля, финальные материалы/бюджет/пересечения), 401 UNAUTHORIZED (включая expiry/revocation), 403 FORBIDDEN (scope/Origin), 404 NOT_FOUND (проект/owner/instance), 409 CONFLICT, 413 TOO_LARGE (HTTP body или MCP UTF-8 args >2 MB), 415 UNSUPPORTED_MEDIA_TYPE, 503 UNAVAILABLE. Формат HTTP/MCP ошибок прежний; индекс операции не добавляется. Ответы статические, без аргументов, секретов, SQL и исходных исключений. Любая ошибка до CAS или проигранный CAS оставляет документ/revision неизменными.

При неизвестном исходе записи MCP возвращает NETWORK_ERROR без retry/redirect и без подстановки новой revision. Повтор уже сохранённого пакета со старой expectedRevision получает 409 без второго применения. Клиент явно перечитывает проект и решает следующую операцию. Автосинхронизации браузера нет: ручная загрузка, подтверждение dirty и stale-save/409 сохраняются.

Живая приёмка требует отдельного согласия на новый QA-проект, конкретные scopes/срок/операции; прежний QA-проект не используется. Preview разрешён, merge/push/production отдельно. Экспорт Java 1.21.5/DataVersion 4325, Sponge v3 и writer не меняются.
