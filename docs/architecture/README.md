# Архитектура mc-commands

Кликабельная C4-документация: [GitHub Pages](https://egorka-dino.github.io/mc-commands/).
Модель описывает код приложения, а не инфраструктуру Telegram-ботов и внешние средства разработки.

## Структура модели

`workspace.dsl` собирает модель через `!include`:

```text
model/
  people-and-systems.dsl      люди и внешние системы
  browser.dsl                 браузерные компоненты
  server.dsl                  серверные компоненты
  shared-command-engines.dsl  общие give/summon engines
  relationships.dsl           связи, объявленные один раз
views/
  static.dsl                  C1, C2 и четыре C3-представления
  dynamic.dsl                 AI-запрос и выполнение сценария
  styles.dsl                  единое оформление
```

`!identifiers hierarchical` позволяет подключать один фрагмент общих генераторов
в оба контейнера без конфликта идентификаторов:
`mc.browser.giveEngine` и `mc.server.giveEngine`. Это два контекста выполнения
одного исходного модуля, а не копии его реализации. Админские и публичные страницы
также используют одни `ItemEditor` и `MobEditor`; редакторы не дублируются в модели.
Представления `editors` и `server-execution` выбирают существующие элементы модели.

Браузер и Next.js-сервер разделены по среде выполнения; они выпускаются одним
Next.js-проектом. localStorage показан внутри браузера. Neon хранит данные приложения,
а Auth.js использует JWT-cookie: таблица сессий в БД не подразумевается.
Диаграммы C4 описывают архитектуру; не каждое поле и не каждый HTTP-запрос вынесены
в отдельный компонент. Схемы взаимодействия показывают успешный пример запроса,
а не все ветвления и повторения алгоритма.

## Просмотр и навигация

Начните с C1. Двойной клик по системе открывает C2, по контейнеру — C3.
Двойной клик по компоненту со ссылкой позволяет открыть исходник в GitHub.
Если переходов несколько, появляется меню. Пробел открывает поиск представлений,
`?` — справку, `c` — масштаб по содержимому. У каждой схемы есть постоянный ключ
в URL, например `diagrams/#server-execution`.

## Локальная проверка и экспорт

Нужны Java 21+, Bash, curl, shasum; Node.js и зависимости сайта не нужны.

```sh
bash tools/architecture/build.sh
python3 -m http.server 8080 --directory .architecture-site
```

Откройте `http://localhost:8080`. Скрипт скачивает закреплённый официальный
Structurizr 2026.09.19 во временный кеш, проверяет SHA-256, проверяет DSL
и экспортирует сайт в `.architecture-site/` (папка исключена из Git).
При необходимости задайте `STRUCTURIZR_WAR` для уже скачанного файла этой версии.
Аргумент скрипта меняет каталог вывода. Загруженный runtime не добавляется
в репозиторий и не входит в зависимости Minecraft-приложения.

Для интерактивной правки раскладки можно использовать `Structurizr local`.
В репозитории источником истины остаётся DSL с автоматической раскладкой;
изменения ручной раскладки из JSON в сборку не включаются.

## Публикация и обновление

GitHub Actions (`.github/workflows/architecture.yml`) проверяет DSL и сохраняет
экспортированный сайт как artifact в pull request. PR не публикует Pages.
После merge изменений архитектуры в `main` workflow обновляет Pages через
`actions/deploy-pages`. Можно также запустить workflow вручную из `main`.

Pages настраивается один раз: Settings → Pages → Source → GitHub Actions.
Окружение `github-pages` должно разрешать публикацию из `main`.
Сайт публичный, поскольку репозиторий публичный; в модель нельзя добавлять секреты,
значения переменных окружения или личные данные. Нужны только названия интеграций
и ссылки на открытые исходники.

При изменении архитектуры меняйте соответствующий фрагмент `model/` и проверяйте
все затронутые представления. При добавлении компонента укажите ссылку на исходник.
Автоматический анализ TypeScript не выполняется: точность модели проверяется в PR.

[общие компоненты](https://docs.structurizr.com/dsl/cookbook/shared-components/),
[экспорт интерактивного сайта](https://docs.structurizr.com/export/static-site).
